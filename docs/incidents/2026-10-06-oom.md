This was not a planned drill. It happened while building the Phase 5 monitoring lab, and it is written up exactly as a real incident would be.

## What happened

| Time (UTC) | Event |
|---|---|
| 05:57 | Production `mysqld` started. Phase 4 had set `innodb_buffer_pool_size = 2G` (sized from the capacity plan). |
| 07:27 | Under the Phase 4 load test, `mysqld` reached **2.95 GB** of the Docker VM's **3.9 GB**. |
| 07:38 | To make room for the replication lab, the buffer pool was shrunk **online** to 768 MB. |
| 07:38–07:39 | The three replication-lab servers and the monitoring stack were started on the same VM. |
| **07:39:32** | The kernel OOM killer killed production `mysqld` (`anon-rss: 3,171,248 kB`; Docker: `OOMKilled=true`, exit 137). |
| 07:39–07:40 | `mysqld` did **not** restart: the production container had no restart policy. |
| 07:40 | DBA saw `mysql_up = 0` for production, then confirmed the OOM kill in `dmesg`. |
| 07:42:00 | `MySQLDown` (critical) notification delivered via Alertmanager, about 2.5 min after the kill, because the rules had not been loaded yet. |
| Not recorded | Recovery steps below remain to be verified and timestamped. |

## Root cause

Several servers were run on a host with no memory budget, and the budget assumed that shrinking the buffer pool frees memory. It doesn't do so reliably:

1. **Shrinking `innodb_buffer_pool_size` online did not shrink the process.** InnoDB released the pool chunks, but the process's resident memory (allocator arenas plus memory used by connections, temporary tables and the adaptive hash index during the load test) stayed at about 3.1 GB.
2. **More servers were started on the same 3.9 GB VM:** three more `mysqld` processes plus Prometheus and Grafana, with no per-container memory limit.
3. **The kernel chose the largest process,** which was production.
4. **Contributing:** no restart policy on the production container, so a crash meant staying down. The alert rules were also not yet active, so detection was manual.

The durability configuration reduces the risk of losing acknowledged writes. With `innodb_flush_log_at_trx_commit = 1` and `sync_binlog = 1`, acknowledged transactions should be durable in the redo log and binlog; recovery and reconciliation still need verification.

## Recovery

The original recovery time was not recorded and cannot be reconstructed from the saved draft. Recovery was subsequently verified on 2026-10-08 after the monitoring drills: all six reconciliation checks passed, the full backup succeeded, and the logical backup succeeded. See [reconciliation evidence](../evidence/phase5/recovery-reconciliation.txt) and [final production drill](../evidence/phase5/production-drill-final.log).

The original recovery procedure was:

1. Start the container and inspect InnoDB crash recovery logs.
2. Run reconciliation and save the output for all ledger invariants.
3. Verify the binlog archiver reconnects and re-run the backup jobs.

## Corrective actions

| # | Action | Status |
|---|---|---|
| 1 | `restart: unless-stopped` on the production container, so a killed `mysqld` comes back in seconds | **done** ([compose](../../docker/standalone/docker-compose.yml)) |
| 2 | `MySQLRestarted` alert (uptime < 5 min), so a crash-and-restart is still visible after the restart policy hides the outage | **done** ([alerts.yml](../../monitoring/prometheus/alerts.yml)) |
| 3 | Memory budget rule: buffer pool + ~1 GB overhead per server, all servers on a host ≤ 80 % of RAM. Lab demos run one lab at a time. | **done** ([docs/05](../05-monitoring.md)) |
| 4 | Restart `mysqld` after shrinking the buffer pool if the memory is needed elsewhere; don't count on online shrink to return RSS | runbook note |
| 5 | Per-container memory limits (`mem_limit`), so one container can't starve the others and OOM stays inside the offending container | proposed |
| 6 | Load alert rules before starting any lab, so detection never depends on someone looking | **done** (monitoring starts first) |

## Lessons

- **Online resizing changes what MySQL allocates, not what the OS gets back.** Capacity decisions have to use measured process RSS, not configuration values.
- **A restart policy turns a crash into a blip**, but only alongside an alert like `MySQLRestarted`. Otherwise crashes become invisible.
- Durable settings (`flush_log_at_trx_commit = 1`, `sync_binlog = 1`) reduce data-loss risk; the later reconciliation verification found no ledger inconsistencies.
